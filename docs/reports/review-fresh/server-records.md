## Findings

### F1 — `?search=%` matches every row: search does not escape LIKE metacharacters
**Severity: medium** · **Confidence: verified**

`server/packages/services/records/src/kysely-record-repository.ts:168`

```ts
function searchCondition(descriptor: EntityRuntimeDescriptor, search: string): RawBuilder<unknown> { const fields = descriptor.fields.filter((field) => field.searchable); if (!fields.length) return sql`FALSE`; return sql`(${sql.join(fields.map((field) => sql`${sql.ref(field.storagePath)}::text ILIKE ${`%${search}%`}`), sql` OR `)})`; }
```

The value is bound (no SQL injection), but it is interpolated into a **LIKE pattern**
without escaping `%`, `_` or the default `\` escape character. The `contains` filter two
lines above explicitly does escape, so the omission is inconsistent and clearly not
intentional:

`server/packages/services/records/src/kysely-record-repository.ts:167,169`

```ts
case "contains": return sql`${ref}::text ILIKE ${`%${escapeLike(String(filter.value ?? ""))}%`} ESCAPE '\\'`; ...
function escapeLike(value: string): string { return value.replace(/[\\%_]/g, (character) => `\\${character}`); }
```

**Why it is wrong.** User search text is treated as a LIKE pattern. `search=%` compiles to
`ILIKE '%%%'`, which is true for every row whose searchable column is non-null;
`search=_` matches any single character; a literal `\` silently becomes an escape prefix.

**Consequence on the shipped Country route.** `GET /api/entity-runtime/country/list?search=%25`
returns the whole country register (all 250 rows) and the exact count badge confirms it.
The browser sends the box contents verbatim (`packages/platform/foundation/api-client/src/entity-list.ts:54,59`:
`const query = state.query?.trim();` … `...(query && query.length >= descriptor.surface.search.minimumQueryLength ? { search: query } : {})`)
and only `trim()`s, so a user typing `%` or `_` gets an unfiltered list with no error.

**What I checked that does not mitigate it.** Route length bound `maxLength: 512` and
`minLength: 1` (`entity-list-routes.ts:243`); `minimumQueryLength` admission
(`query-service.ts:204-211`); "at least one searchable readable field"
(`query-service.ts:545-553`); hidden search fields are removed before the repository
(`query-service.ts:228-236`). None of these escape or reject metacharacters. The in-memory
repository does **not** have the bug (`in-memory-record-repository.ts:34` uses literal
`.includes(needle)`), so the existing suite cannot observe it.

**Fix.** Reuse the existing escaper:

```ts
return sql`(${sql.join(fields.map((field) => sql`${sql.ref(field.storagePath)}::text ILIKE ${`%${escapeLike(search)}%`} ESCAPE '\\'`), sql` OR `)})`;
```

and add a repository test that `search: "%"` returns only rows containing a literal `%`.

### F2 — The list descriptor advertises a synthetic `record_id` field that the list route rejects
**Severity: medium** (latent: not reachable for Country, breaks the next entity whose id column is unpublished)
**Confidence: verified** for the code path; the Country route itself is unaffected

`server/packages/services/records/src/entity-list-service.ts:900-913`

```ts
  if (!storageIdentity.published && identityKey === storageIdentity.key)
    fields.unshift(
      Object.freeze({
        key: storageIdentity.key,
        label: "Record ID",
        valueKind: "string",
        defaultVisible: true,
        defaultOrder: 0,
        filterOperators: Object.freeze([]),
        sortable: false,
        groupable: false,
        aggregations: Object.freeze([]),
      }),
    );
```

`storageIdentity.key` is `"record_id"` (`entity-list-service.ts:1322-1332`) and this synthetic
field is `defaultVisible: true`, so it lands in `surface.defaultState.columns`
(`entity-list-service.ts:925-927`). But the query admission for a `fields` projection only
accepts keys that exist in `descriptor.fields`:

`server/packages/services/records/src/query-service.ts:538-544`

```ts
  for (const field of query.fields ?? [])
    if (!map.has(field) || !readable.has(field))
      throw new RecordServiceError(
        400,
        "PROJECTION_FIELD_NOT_ALLOWED",
        `Field is not readable: ${field}`,
      );
```

`record_id` is not a `descriptor.fields` entry, so `fields=["record_id", ...]` is a 400.

**Why it is wrong.** The server publishes a field that it tells the browser to display by
default and then refuses to accept back in the projection it controls. The browser's base
state is the descriptor default state (`packages/contracts/platform/entity-list/src/url-state.ts:106`
`parseSaveableListState(state ?? descriptor.surface.defaultState, descriptor)`) and
`entityListQuery` sends `fields: state.columns` whenever columns are non-empty
(`api-client/src/entity-list.ts:60`). So the *first, unmodified* list request contains
`record_id`.

**Consequence.** For any table-backed entity whose published fields contain no readable
field with `storagePath === storage.idField`, every list page fails with
`400 PROJECTION_FIELD_NOT_ALLOWED`. Country is **not** affected because
`metadata/products/shared/entities/country/definition.json` publishes an `id` field bound to
the `id` column, so `storageIdentity.published === true` and `record_id` is never injected.
This is the framework defect that the next onboarded entity can hit.

**Fix.** Either accept the synthetic identity key in `validateQueryFields`/`responseProjection`
(map it to `descriptor.storage.idField`), or do not mark it `defaultVisible`, or do not
advertise a `fields` key the route cannot accept. Add a round-trip test that feeds
`descriptor.surface.defaultState.columns` straight back into `list()`.

### F3 — `countMode` metadata is unenforced; `cached`/`approximate` are accepted but unimplemented
**Severity: medium** · **Confidence: verified**

`server/packages/services/records/src/entity-list-service.ts:1086-1094`

```ts
    limits: Object.freeze({
      defaultPageSize,
      allowedPageSizes: pageSizes,
      maxSortLevels,
      countMode:
        configuredLimits?.countMode ??
        descriptor.listPresentation?.countMode ??
        "none",
    }),
```

is the only place `limits.countMode` is read. The executed mode is whatever the client sends:

`server/packages/services/records/src/query-service.ts:241`
```ts
            countMode: query.countMode ?? "none",
```
`server/packages/services/records/src/kysely-record-repository.ts:49-55`
```ts
      if (input.countMode === "exact" && groups) {
        total = groups.reduce((sum, bucket) => sum + bucket.count, 0);
      } else if (input.countMode === "exact") {
        const count = await sql<{ count: string | number | bigint }>`SELECT count(*) AS count FROM ${table(input.descriptor)} WHERE ${sql.join(conditions, sql` AND `)}`.execute(executor);
        total = Number(count.rows[0]?.count ?? 0);
      }
      const countMode = input.countMode === "exact" ? "exact" : "none";
```

**Why it is wrong.** (a) The published `limits.countMode` is advisory only: a client may send
`countMode=exact` for an entity whose metadata declares `none` or `cached`, forcing an
unbounded `SELECT count(*)` over the whole filtered set (no `LIMIT`). (b) The route and parser
accept `cached` and `approximate` (`entity-list-routes.ts:271-274`,
`records-routes.ts:66`) but the repository implements only `"exact"`; any other value
silently degrades to `countMode: "none"` with no `total`, which is surfaced only as
`requestedCountMode` (`entity-list-service.ts:711-714`).

**Consequence on the shipped Country route.** Country declares `countMode: "exact"`
(`graph-builder.ts:68`), so the browser requests `countMode=exact` on every page
(`api-client/src/entity-list.ts:64`) and each page issues one extra full `COUNT(*)`. At
~250 rows this is immaterial, but the "metadata declares the allowed count mode" control is
not enforced anywhere, and an entity declaring `cached` will silently render no total.

**Fix.** In `query-service`, reject or clamp a requested `countMode` that exceeds
`descriptor.listPresentation?.limits?.countMode`, and either implement `cached`/`approximate`
or refuse them with a typed error instead of silently returning `none`.

### F5 — The legacy GET list returns raw repository rows, including storage columns that were not requested or readable
**Severity: low** (not exposed through the BFF relay) · **Confidence: verified**

`server/packages/services/records/src/query-service.ts:342-361`
```ts

  // optimistic concurrency, but query-internal sort columns never escape.
  for (const key of [
    descriptor.storage.idField,
    descriptor.storage.versionField,
    descriptor.storage.statusField,

    if (key) visible.add(key);
  return Object.freeze({
    ...result,
    data: Object.freeze(
```

`createRecordQueryService.list` returns the executor result **directly to HTTP**, so the

**Fix.** Strip storage-only coordinates before serialising an HTTP response (keep them for the

### F6 — Grouped lists run an unbounded `GROUP BY` and return every bucket
**Severity: low** (unreachable for Country) · **Confidence: verified**

`server/packages/services/records/src/kysely-record-repository.ts:47`
```ts
      const groups = input.group ? await groupBuckets(input, conditions, executor) : undefined;
```
`server/packages/services/records/src/kysely-record-repository.ts:171`
```ts
async function groupBuckets(input: RecordRepositoryListInput, conditions: readonly RawBuilder<unknown>[], executor: RecordDatabase | RecordTransaction) { const ref = sql.ref(fieldPath(input.descriptor, input.group!)); const result = await sql<{ value: unknown; count: string | number | bigint }>`SELECT ${ref} AS value, count(*) AS count FROM ${table(input.descriptor)} WHERE ${sql.join(conditions, sql` AND `)} GROUP BY ${ref} ORDER BY ${ref} ASC`.execute(executor); return Object.freeze(result.rows.map((row) => Object.freeze({ value: row.value, count: Number(row.count) }))); }
```

### F7 — `filter` items have no size bound while `search` and `cursor` do
**Severity: low** · **Confidence: verified**

`server/packages/services/records/src/entity-list-routes.ts:251-259`
```ts
    filter: {
      oneOf: [
        { type: "string" },
        {
          type: "array",
          maxItems: MAX_LIST_FILTERS,
          items: { type: "string" },
        },
      ],
    },
```
(the same shape is in `records-routes.ts:44`.) Only the array cardinality is bounded
(`MAX_LIST_FILTERS = 20`, `list-limits.ts:7`). `search` is capped at 512 and `cursor` at 4096,
but each filter JSON string is unbounded, so a `contains` value (or any of the up to 100 values
of an `in` filter, `records-routes.ts:90`) can be as large as the HTTP request line permits.
**Consequence.** No injection — values are bound parameters — but an authenticated caller can
push large LIKE patterns/`IN` lists through the read path with no service-level ceiling.
**Fix.** Add a `maxLength` to filter items and/or bound parsed values in `parseFilter`.

## Checked but not a defect

* **`?search=%` returning everything** is reported as F1, not here.
* **`usesEntityBackendAuthorization` is currently always false.** No composition passes
  `entityBackends` (`server/apps/platform-host/src/composition/register-services.ts:374` only
  declares the option; `:550-570` reduces over an empty list), and the base permission
  authorizer defines no `enforcedEntityProfile`. Therefore the V2 canonical admission,
  the per-row authorization loop (`query-service.ts:294-310`) and `executeAuthorizedAggregate`
  are dormant. This is rollout gating, not a bypass: the coarse path still enforces permission,
  operation binding, tenant boundary and record ACLs. Country is public reference data in any case.
* **A dormant aggregate cursor defect.** `authorized-aggregate.ts:77-80` calls
  `repository.list({ ...query, recordIds: ids }, ...)` while `query` may still carry the client
  cursor; `binding()` includes `recordIds` (`record-cursor.ts:43`), so a cursor + `group`/`exact`
  request on an enforced entity would fail `400 INVALID_CURSOR`. Not reachable today because the
  aggregate path requires `enforced === true`, so I did not raise it as a finding.
* **The `scope_not_contained` retry in `authorizeRecordListRead`** (`record-read-access.ts:36-43`)
  looks permissive but is fail-closed: for a principal whose only allow evidence is `record_acl`,
  the resource-free retry returns `resource_required`
  (`permission-authorizer.ts:97-104`), so a record-scoped grant cannot become a tenant-wide read.
* **Ajv `format: "uuid"` is not enforced** (Ajv2020 is constructed without `ajv-formats`,
  `server/packages/runtime/http/src/route-contract.ts:40`), but
  every such parameter is re-validated in the handler (`parseEntityListScopeCoordinate`,
  `recordId`), so no unvalidated value reaches SQL. `maxLength`/`pattern`are enforced.
* **Client entity-code guard is looser than the server's.** `api-client/src/entity-list.ts:83-87`
  accepts `^[a-z][a-z0-9_.-]{0,126}$` while `isCanonicalEntityCode` requires
  `^[a-z][a-z0-9_]{1,62}$`; the app only ever sends a descriptor-supplied code and the server
  rejects the rest with `400 INVALID_ENTITY_CODE` (`__tests__/entity-list-read-routes.test.ts:74-79`),
  so this is defence-in-depth, not a bypass.
* **`MISSING_PERMISSION` route audit** (`server/packages/runtime/http/src/route-contract.ts:88`)
  is unsatisfied by the entity-runtime contracts (they carry no `permission`), but
  `auditRouteContracts` is never invoked in the app and permissions for these routes are
  per-entity metadata resolved inside the service.
* **`idField: "id"` is hardcoded** when the host builds the publication registration
  (`server/apps/platform-host/src/composition/shared/publication/compiled-runtime.ts:115`) with no
  check that a field/column named `id` exists. Current shared-reference and table entities have an
  `id` primary key (`shared.country`, `document.entity_case:51`, `master.business_partner:1866`)
  and Country publishes an `id` field, so this is not reachable today; it is the precondition behind
  F2 rather than a separate finding.
* **`entity-list-service.record()` does not call `requireOperation`**, but it delegates to
  `queries.get`, which authorizes (`query-service.ts:398-409` / `383-397`) before any read.
* **Per-row authorization is sequential** (`query-service.ts:294-310`), i.e. up to 100 awaited
  decisions per page, and `readableRecordFields` issues one authorization per field in parallel.
  For Country the field loop short-circuits to zero calls (no `readPermissionCode`, no enforced
  profile) and the row loop is dormant, so there is no current N+1 on the shipped route.
* **`groupBuckets` unbounded** is reported as F6, not repeated here.
* **`countMode: "cached"` in the query contract test** (`__tests__/records-query-contract.test.ts:15,25`)
  shows accepting the value is intentional at the parse layer; the defect is that the repository
  neither implements nor rejects it (F3).
