Entity Designer — composition tree

An alternative to the flat table browser in prototype v2. Most metadata.entity_* tables are not independent objects — they are ordered children of a parent (surface → section → field binding; key → key field; relation → target → field mapping). This view navigates that real nesting directly instead of asking you to find the right parent ID in a dropdown on a separate screen.

Business Partner composition

Same descriptor/validator engine as v2
What's different from v2 — nodes are rendered recursively from a small CHILDREN map (which table is a child of which, matched by real foreign keys such as entity_surface_section.parent_section_id), so entity_surface_section nests under itself exactly like the DDL's self-referencing constraint allows. Adding a child pre-fills its parent scope automatically; nothing asks you to pick a UUID from a list.

Where this helps vs. the flat browser

SituationFlat table browser (v2)Composition tree (v3)
Add a field binding to a specific sectionOpen entity_surface_field_binding, pick surface from a list of IDs, pick section from another list of IDsExpand the section, click "+ Add entity_surface_field_binding" — both IDs are already correct
Understand a form's actual layoutCross-reference three separate flat tables by IDRead top-to-bottom in the tree, same order as the compiled surface
Reorder membersEdit a position integer with no view of siblingsMove up/down against visible siblings; positions renumber automatically
Audit or bulk-scan every row of one table (e.g. every deprecated field across all entities)Better fitRequires walking every tree

Recommendation: keep both. The composition tree is the default editing surface; the flat browser in v2 stays as a power-user/inspector view for cross-cutting queries the tree is bad at.
