# Internal and External Workforce — SAP benchmark and table/field analysis

Review date: 2026-09-21. Baseline: current working-tree DDL, not a live database. SAP comparison uses public SAP documentation retrieved for this review. Proposed Athyper tables/fields below are design recommendations, not implemented migrations or SAP's physical schema.

Delivery sequence: [Stage 1 Internal / Stage 2 External](hr-internal-external-implementation-plan.md). Existing field evidence: [2,042 declared columns across 103 selected manifest-listed tables](hr-workforce-current-fields.csv). Proposed changes: [67-item field change register](hr-workforce-field-changes.csv). The catalog includes supporting IAM, contacts, banking and finance tables; it is not 103 HR-specific tables. It supplements the earlier [95-table inventory](hr-ddl-inventory.csv) with contact/address/external-reference and rate-policy definitions.

## 1. Comparison boundaries

| Benchmark | Documented SAP capability | Athyper baseline and design implication |
|---|---|---|
| Employee Central job data | EmpJob is effective dated and keyed by userId/startDate/seqNumber, with a latest-change indicator. [SAP EmpJob](https://help.sap.com/docs/successfactors-platform/sap-successfactors-api-reference-guide-odata-v2/empjob) | work_assignment has date ranges but no explicit same-day business sequence. Add revision semantics and deterministic as-of queries; do not equate SAP userId with our login principal_id. |
| Employee Central history | Effective-dated records support historical/future states; SAP describes automatically closing the preceding date slice. [SAP effective dating](https://help.sap.com/docs/successfactors-platform/sap-successfactors-api-reference-guide-odata-v2/effective-dating) | Adopt explicit effective dates and recorded correction history. Athyper uses exclusive end dates in assignments; an SAP adapter must translate inclusive end dates, not copy them unchanged. |
| Concurrent employment | A concurrent employment uses an existing person identifier and creates another employment/user identifier in the SAP process. [SAP concurrent employment](https://help.sap.com/docs/successfactors-employee-central/implementing-employee-central-core/importing-concurrent-employments-for-employees) | Preserve one person and multiple employment contracts. | Global assignment | Home and host employments are linked for a temporary company assignment. [SAP global assignment](https://help.sap.com/docs/successfactors-employee-central/employee-central-scope-items/manage-global-assignment) | Existing multiple employment rows are not enough to explain home/host relationship or return. Add a global-assignment document. |
| Event reasons | Reasons classify hire, rehire, transfer, promotion and other employee changes and can affect employee status. [SAP event reasons](https://help.sap.com/docs/SAP_SUCCESSFACTORS_EMPLOYEE_CENTRAL/b14dd15ca58f43e0856184a740a4b212/67bdc75d869a43db961b1e981b38b7aa.html) | Introduce controlled reason/version references and event evidence instead of free-text-only explanations. |
| Job relationships | HR, matrix, second and other manager relationships are effective dated and can participate in workflows. [SAP job relationships](https://help.sap.com/docs/successfactors-employee-central/implementing-employee-central-core/job-relationships) | manager_employee_id supplies one reporting line; add typed relationships with independent workflow and visibility rules. |

[SAP personal data](https://help.sap.com/docs/successfactors-employee-central/implementing-employee-central-core/personal-data) | Single national-ID/passport slots and emergency_contact JSON need structured multi-valued records. | Pay components | SAP distinguishes recurring/one-time components and amount/percentage/unit-related values. [SAP pay components](https://help.sap.com/docs/successfactors-employee-central/implementing-employee-compensation-data/pay-components) | Athyper already has is_recurring, value_type and taxable_behavior. Extend employee-level assignments and versioned calculation policy; do not add duplicate flags. |
| Time Off | Time accounts bound entitlements and bookable periods, with accrual and period-end processing. [SAP time accounts](https://help.sap.com/docs/successfactors-employee-central/implementing-time-management-in-sap-successfactors/time-account-types), [SAP time calendars](https://help.sap.com/docs/successfactors-employee-central/operating-time-management-in-sap-successfactors/calendars-in-time-off) | Enrollment plus ledger is a good foundation. Add explicit account periods, reservations and rule/job evidence, avoiding double-counted opening balances. |
| Talent suite | SAP's talent offering spans candidate journeys, skills/learning, goals/feedback, compensation planning and succession. [SAP talent tour](https://www.sap.com/products/hcm/talent-management/product-tour.html) | Add typed learning/performance/recruitment/planning records. These are broader suite capabilities, not all Employee Central core. |
| External workforce | Fieldglass covers contingent workforce, services procurement, assignments and worker profiles. [SAP Fieldglass](https://learning.sap.com/products/intelligent-spend-management/fieldglass) | Existing external-worker/engagement/work-order/SOW structures are the correct comparison point. | External tenure | Fieldglass documents consolidated tenure tracking and tenure-driven rate policies. No percentage parity or superiority score is assigned. Table existence, source code, licensed SAP product capability and qualified deployment are different evidence categories. SAP behavior varies by product/version/configuration. The suggested improvements target Athyper's current baseline.

## 2. Model conventions for the proposed changes

- `!` means required after validated backfill; `?` means optional. Types are proposed PostgreSQL types. UUID references use tenant-composite foreign keys unless the target is a documented global reference.
- New master/document rows generally require `id uuid`, `tenant_id uuid`, `created_at timestamptz`, `created_by uuid`; mutable records add paired update audit and optimistic `row_version bigint`. Append-only evidence uses source/recorded timestamps and immutable actor references instead of an editable row version.
- Adopt `[effective_from,effective_until)` for proposed ranges. Translate legacy inclusive fields explicitly; do not silently change existing payroll/leave date semantics.
- A historical revision model needs both effective time and recorded time. An updated_at column alone cannot answer what a reviewer knew when approving a backdated change.
- For same-day changes, retain all revisions with sequence/correction lineage but expose one applicable published revision per subject/date. Adding sequence_no to existing tables without redesigning overlap exclusions will not work.
- Proposed status/reason/classification codes require governed domains/reference catalogs and allowed transitions, not unrestricted text merely because examples below say `text`.
- Reuse platform workflow, command execution, audit, content, external references, metadata extension and authorization infrastructure. Add HR-specific data contracts where generic storage cannot enforce the relationship. Do not create another generic workflow engine.
- P0 = initial correctness/privacy blocker; P1 = process foundation; P2 = later full-module capability. Priority does not remove an accepted capability from final delivery.

## 8. Specific improvements to prioritize

1. **History that explains changes.** Effective range plus sequence, event reason, source request and recorded correction lineage. User-visible before/after diff and as-of date avoid unexplained current-state overwrites.
2. **One person, distinct workforce relationships.** Employee and external-worker roles can coexist. Counts distinguish unique people, employment headcount, FTE and active engagements. A User app is an access administration surface, not the employee database.
3. **Usable permission boundaries.** Employee/manager/HR/payroll/procurement/supplier views use the same section contracts with different scope and protected fields. Record existence, related counts and exports obey those rules.
4. **Reproducible decisions.** Pay, leave, readiness, rate, tenure and eligibility decisions reference the rule and input versions actually used, with safe explanations in 360 views.
5. **Distinct business and integration completion.** Approved employment, IAM delivery, accepted service, posted payable and successful payment each have their own state and recovery action.
6. **Renewal without history loss.** Contract changes, compliance renewals, compensation changes and profile corrections append evidence. Active projections can be rebuilt from accepted revisions.
7. **Shared infrastructure with typed HR contracts.** Reuse external_reference, contacts, banking, workflow and content; add missing domain records instead of hiding entitlements, dependants, contract terms or money in unrestricted metadata.

These are proposed Athyper design goals, not assertions that SAP lacks these behaviors. Optional AI assistance can later explain authorized records or draft requests; it should not be a prerequisite for core delivery or automatically determine hiring, promotion or termination.

| Commercial revision binding | Infer from accepted evidence/date when unique; quarantine ambiguous prior terms; composite supplier/company/contract checks; frozen claim source references | Later rate revision cannot alter old approved invoice/time value; shared SOW cap cannot be overspent |

Published schemas/metadata/API serializers and old clients must be handled alongside DDL. Run relevant PostgreSQL integrity/concurrency tests, API authorization tests and browser workflows; preserve rollout/backfill reconciliation reports.

## 10. What is verified and what remains open

Verified from source: named current columns and declarations in the companion CSV; selected constraints/views/guards described above; existing workforce services/routes; public SAP capability documentation. The CSV records CREATE TABLE declarations including explicit NOT NULL/default/generated text. It is not live introspection and does not flatten later ALTER TABLE constraints, domain rules or every runtime grant into an effective schema.

Open implementation decisions: exact payroll countries, localized personal attributes, multi-employment payroll aggregation, global-assignment policies, staffing/dates, split shifts, advanced recruitment/talent integrations, and whether existing shared policy/ledger mechanisms fully cover each proposed child table. No new table is required merely to imitate an SAP entity name. Detailed migrations must resolve reuse versus new storage before implementation.

Immediate implementation order: S01/I02/S11 correctness → Employee 360 I1 → stable event/revision/relationship contracts I2/I3 → time/pay/leave and broader internal delivery → Stage 1 qualification → external revision/readiness/tenure/compliance enhancements and Stage 2 delivery. Existing external capabilities remain supported throughout.
