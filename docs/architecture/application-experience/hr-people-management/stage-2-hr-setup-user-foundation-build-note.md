# Stage 2 HR setup and User foundation — build status

> **Historical.** Written before commit `870f08f52` removed the bespoke Business Partner and workforce applications. Routes, packages and files named here may no longer exist, and de-linked paths were dead when this was cleaned up. New entity work goes through the shared Entity Framework ([onboarding guide](../../../runbooks/meta-entity-onboarding.md)); do not treat this as current instruction.

**Status: in progress, 2026-09-22.** Setup, policy applicability, User profile commands and authority projection now have working vertical paths.

The Neon application now has `/people/workforce/hr-setup`, `/people/workforce/users`, `/people/workforce/users/[principalId]`, and `/people/workforce/users/me/profile-change`. They use the platform relay and server-side authorization. The Employee directory links to each surface only when the browser permission snapshot permits it. The server independently checks each permission and never fetches denied setup or User data. Responses use `private, no-store`.

The HR setup catalog reads the selected company's country, jobs and families/functions, grades, positions, organizations, sites, holiday calendars and available HR policy definitions. Because `master.org_unit` has no company key, organization scope is established by a current published company–organization link or legacy position/work-assignment evidence. A user with company-scoped `neon.hr.setup.write` can create a **draft** position with an effective date. The command checks that job, organization and site references are active and in scope, rejects conflicting codes, and writes audit evidence. It does not publish the position or change historical employee assignments. Applicable policy versions are resolved by country/company/site scope and effective date; where `neon.policy.simulate` is granted, the screen calls the existing simulation service and shows its decision and explanation.

The User directory is tenant-scoped and shows principal type/status and primary identity-binding sync status. The detail includes profile, catalog language (`language_code`), formatting locale (`locale_code`), timezone and format preferences, identity-binding diagnostics, membership and group/role/scope facts. Identity subject IDs and sync error messages are not returned to this screen. The self-service command accepts preferred/display name only, verifies an active `user` principal, and creates a draft `document.user_profile_update_request` with `created_by = requested_by = principal_id`. It supports idempotent replay, rejects a changed payload under the same key and refuses a second active request. It does not directly update the principal profile.

The new permission definitions are seeded in `server/db/ddl/planes/neon/authz/20_hr_stage2_permissions.sql`: company-exact setup read/write and tenant-exact User read/self request. Setup write and User directory read require MFA. `server/db/scripts/provisioning/provision-hr-stage2-local-access.sql` grants these permissions through separate managed roles to the existing Stage 0 synthetic admin group and scopes; it is a local demo fixture, not a general tenant grant.

Verification completed locally: service, platform host, Neon app, relay and Workforce package typechecks; the Stage 2 authorization-boundary unit test; and `hr-stage2-setup-user.sql` executed as `athyper_runtime` in a transaction that inserted and reloaded a draft position and a self-only request, proved cross-user request rejection, then rolled back. The service-level `hr-stage2-service.mts` probe exercises setup, User and policy paths within a rolled-back transaction. The local permission definitions and scoped role bindings were inspected after seeding, and re-running the local access seed succeeded without duplicate grants. The hot-reloaded API returned 401 on an unauthenticated Stage 2 route request, confirming route mounting and authentication. The later authenticated browser check covers setup access, denied data loading and a synthetic policy simulation; it does not validate a real country rule.


The follow-up migrations add `master.hr_policy_assignment` (version/hash pinned, country/company/site scoped, date effective and separately reviewed), profile-request reviewer/version columns, tenant-admin User RLS access and permission definitions. Policy resolution selects site over company over country on an as-of date and explains lower-priority versions. Draft creation is idempotent; publication requires another principal and rejects overlapping active intervals at the same scope. The local HR policy definition is synthetic; its rules do not prove leave or payroll calculation.

A submitted self-request can now be approved or rejected from a separate review queue. Approval applies only preferred/display name to an active human principal, uses optimistic versions and records audit; an admin can issue a separate direct profile command. The Employee 360 authority endpoint projects self, current manager, exact-company approved delegation and HR access from current approved employment/assignment relationships. It is a read projection, and manager/delegation command enforcement remains open.

## Governed setup follow-up (2026-09-22)

A shared publication register (`master.hr_setup_publication`) now captures pending and published new HR setup records. The seven supported create forms are job family, job function, pay grade, job, position, site and holiday calendar. Tenant catalog creation/publication uses separate exact-tenant permissions; position/site/calendar creation/publication uses exact-company permissions. Creation validates active references and scope. Publication locks the approval record, checks its version and draft source, requires a different actor, updates the source and receipt atomically, and writes audit evidence. The earlier quick-position command now registers its drafts in the same approval flow. Existing active setup records are not edited or retrospectively versioned by this increment; holiday calendar days and explicit company–organization references remain open.

The User detail can invoke the existing Workforce IAM projection retry for an active employment link when the actor has `neon.workforce.iam.retry`. It queues an intent for the asynchronous worker; it is not a direct TrustIAM or provider mutation. The HR policy simulation picker now selects only an effective published version with a rule count above zero; the local synthetic definition has zero rules and cannot be mistaken for a leave/payroll calculation.

The local migration and permission seed were applied to the development database. A rolled-back service probe created and published all seven setup kinds, rejected maker self-publication and a duplicate publication, and rejected a wrong-company draft. Server, relay, Workforce and Neon typechecks passed. The authenticated browser walkthrough loaded the governed setup register for the allowed actor; a denied actor received 403 for both catalog and draft creation. Manager/delegation authority is still a read projection; command enforcement and a delegated-manager browser fixture remain open.

A local-only synthetic `hr.leave.demo_eligibility` policy was authored with two expression rules and two passing test cases, then activated by a different principal and assigned to the synthetic company through the Stage 2 publication flow. The authenticated browser simulated an eligible request and received an `allow` explanation; the provisioning script also verified the ineligible `deny` branch. The script is [provision-hr-stage2-synthetic-policy.mts](../../../../server/db/scripts/provisioning/provision-hr-stage2-synthetic-policy.mts). It uses the local privileged database account because the Neon runtime role intentionally cannot author `control.policy_definition`. The example is explicitly synthetic and contains no statutory leave entitlement or payroll formula. Real country/company HR policies and calculation integration remain open.

## Effective references and calendar days

`master.hr_org_company_assignment` adds an effective, independently published company link for an active tenant organization unit. The HR setup catalog and draft-position validation now recognize current published links alongside legacy position/work-assignment evidence. Published links reject overlapping active periods for the same organization/company. Drafts cannot start in the past; existing employment and work-assignment history is unchanged.

`master.hr_calendar_day_change` holds a separately reviewed proposal for a future date in an active company calendar. Publication inserts the canonical `master.holiday_calendar_day` once and pins the inserted row in the approval record. A past/current date, a duplicate date, an inactive or wrong-company calendar, maker self-publication and stale version are rejected. Editing a published or historical calendar day is intentionally still open because it needs revision semantics and downstream calculation impact analysis.

The rolled-back service probe created/published an organization link and future calendar day, reloaded both, verified the canonical day, and exercised the rejection cases. The authenticated HR setup browser loaded the two new sections and returned 200 from their independently scoped endpoints.

The rollback service probe also temporarily linked a synthetic employee to a User principal, reloaded the User detail employment link, and invoked the existing internal Workforce IAM identity-intent command with the linked active employment. All changes rolled back. The authenticated browser used for the local walkthrough did not satisfy the existing MFA requirement on User directory detail (403), so a linked-user browser action remains unverified. The temporary committed browser fixture was restored to its original unlinked state; the MFA rule was not weakened.
