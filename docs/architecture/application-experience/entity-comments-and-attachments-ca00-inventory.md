## Entity admission and fixtures

Business Partner is the first write-capable parent and must use its published record scope and authorization. `atlas-attachment-knowledge.ts` already demonstrates the required pattern: load the current descriptor, query the authorized record membership through the Records service, and accept exactly the requested record ID.

`customer` is the second real entity. Its Core artifact currently disables comments and attachments, and its operation artifact exposes `read` plus governed `request_change`; the authorization inventory identifies `master.customer` as externally readable and not externally writable. CA-10 can enable an appropriate published, read-first collaboration fixture after CA-01–05 admission is in place. It must use the same generic record admission path and needs no Customer-specific layout. Currency remains unchanged and is not made writable for this demonstration.

Use a fresh disposable Neon database, isolated object-storage and queue namespaces, one seeded Business Partner, one seeded Customer, an authorized collaborator, a denied principal, and small synthetic image/PDF files. Keep the existing local database and stored objects intact.

## Actual current interface versus proposed definition keys

The active local release above supports the source-wired basic service operations: comment create/edit/delete; attachment stage/finalize/status/download/delete; and renderer keys `platform.comments.v1` / `platform.attachments.v1`. These are not yet the accepted shared experience. JSON fields shown as `proposed_requires_catalog_verification`, richer attachment policy, comment audiences beyond the present reader behavior, folders/categories, revisions, derivatives, search, shared drawer URL state and preview are proposed work until CA-01–09 wire and validate them.
