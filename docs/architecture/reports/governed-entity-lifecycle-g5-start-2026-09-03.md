# Governed entity lifecycle G5 start — 2026-09-03

G5 is open. This slice establishes the first executable external-worker IAM contract and records an honest rollout matrix; it does not assert the live three-plane exit gate.

## Landed

- `trustiam.identity_projection` now treats `external_worker` as an engagement-scoped relationship and adds unique tenant, source plane/tenant, relationship-kind and source-reference correlation. The existing one-projection-per-Person and realm-identifier uniqueness boundaries remain intact; Person is not treated as the engagement lifecycle authority.
- The IAM saga accepts `worker_engagement:<id>` only for an employer-purpose organization, forwards that relationship to the provider, and uses its existing exact desired-version/hash fencing, local-first revocation, retry and maker-checker replay boundaries.
- A Studio supported-upgrade migration now constructs the canonical projection when the upgrading database predates it, then validates historical relationship/source pairs and duplicate source coordinates before adding source uniqueness, tenant/organization FKs, the reconciliation index and extended relationship checks.
- Unit evidence covers external-worker provisioning and termination deprovisioning without invoking identity creation on termination. Static evidence rejects deletion of Person, external-worker or worker-engagement authority.
- `governed-lifecycle-g5-readiness.v1.json` assigns every G5 scenario an owner, current evidence and executable exit gate.
- NEON now exposes one security-definer worker-engagement IAM projection command. It validates plane/tenant/actor context, serializes commands, distinguishes not-found and stale-version failures, maps lifecycle to active/suspended/deprovisioned intent, and atomically updates `access_status`, writes exact desired-state outbox content, and completes generic command evidence.
- A trigger rejects direct `worker_engagement.access_status` changes unless the matching command execution is processing. The command is revoked from `PUBLIC` and explicitly granted to application/admin roles.
- The supported-upgrade migration compiled and committed on the running local NEON database. A rollback-contained live probe passed active intent, exact replay, conflicting replay, stale version, command-only access mutation, forced rollback, suspension, termination, cross-tenant rejection and source-authority preservation.
- Studio now has a strict external-worker intent consumer. It rejects unknown envelope/application/role keys, mismatched tenant and scope coordinates, oversized content and invalid hashes; its repository applies only monotonic desired versions and records applied, replayed, stale or conflicting outcomes with command evidence and an acknowledgement outbox row in one transaction.
- Platform-host now wires a dedicated leased NEON-to-Studio delivery worker. It claims only `neon-workforce-iam` events with `FOR UPDATE SKIP LOCKED`, resolves a tenant-local Studio actor, completes exact recipient dispositions, applies bounded exponential retry for missing dependencies, dead-letters unsafe envelopes, publishes backlog health and schedules 100-row batches every 15 seconds.
- The corrected Studio migration applied to the running supported-upgrade database that did not yet contain `trustiam.identity_projection`. A rollback-contained cross-database probe then used the production delivery repository and Studio consumer to prove missing-organization retry, recovery after adding a tenant-matched organization, atomic projection/command/ack evidence and exact redelivery without duplicate acknowledgement. All Person, worker, engagement, organization, projection and outbox probe fixtures were rolled back.
- Live delivery exposed that NEON command executions use UUIDv7; the Studio contract now admits RFC UUID versions 1–8 and has a focused UUIDv7 regression test.
- Studio saga persistence now accepts an injected transaction runner, allowing live certification to contain all Studio fixtures in the same rollback boundary. Every terminal saga attempt writes a bounded `iam.authority` outbox receipt atomically with its fenced attempt/projection transition.
- A supported-upgrade migration constructs the previously absent `identity_saga_attempt` authority with projection/replay FKs, open-attempt uniqueness, retry indexes, immutable terminal evidence, desired-state fencing, RLS and service grants.
- The live probe recovered from a transient provider failure, provisioned NEON principal identity, plane admission and an exact legal-entity role scope, then suspended and deprovisioned it. The principal `auth_epoch` advanced from 0 to 1 to 2; four saga attempts produced four audit/outbox receipts; Person, external-worker and engagement rows remained unchanged and every fixture rolled back.
- A production Keycloak Admin adapter now resolves its client credential only through an opaque secret-store reference, requires HTTPS outside loopback, uses bounded client-credentials requests, performs exact/idempotent user and organization-membership operations, classifies throttling and server faults for retry, and disables rather than deletes identities during suspension or deprovisioning. Secret bytes are cleared after token exchange and are not written to saga evidence.
- Platform-host validates the Keycloak administrator settings as an all-or-none group and conditionally registers the saga only when Studio, NEON and MESH job databases plus the secret store are available. The same worker now maps all three plane-local target adapters, runs a bounded scheduled batch, emits health/metrics and captures dead letters.
- Contract routes now expose maker-checker replay under `studio.iam.application_projection.replay` and a bounded, `no-store` evidence view under `studio.iam.application_projection.read`. The evidence response deliberately excludes provider subject and login identifier.
- The rollback-contained probe now creates a terminal fifth attempt, rejects self-approval, accepts a distinct elevated approver, records that approver, and verifies that the application role can read the attempt only in the correct tenant through RLS. Five saga attempts and five atomic audit/outbox receipts are observed before rollback.
- A guarded disposable PostgreSQL 16.13 container provisioned all canonical manifests from empty Studio, NEON and MESH databases: 228, 207 and 207 ordered entries respectively. All three builds completed successfully and the disposable container was removed.
- A fresh Keycloak 26.7.2 container then proved the production adapter with a disposable realm, confidential service-account client and organization. Exact create replay returned one subject, membership was visible through the provider API, and suspension plus deprovisioning both left that subject disabled rather than deleted. The realm and container were removed after success.
- The rollback-contained supported-upgrade probe now supplies Studio, NEON and MESH applications to the production plane-local authority. All three planes created an isolated principal, Keycloak binding and active admission, then advanced `auth_epoch` from 0 to 1 to 2 while suspending and terminally deprovisioning access. Only NEON received the deliberately scoped workforce role; Studio and MESH did not infer grants from provider membership.

It starts fresh PostgreSQL 16.13 and Keycloak 26.7.2 containers, installs all three canonical manifests, applies the canonical three-plane tenant/authorization seed and existing Business Partner fixture pack, creates a disposable provider realm/client/organization, and runs the production external-worker transport and saga through the real provider and every local plane. It emits `G5_COMBINED_CLEAN_KEYCLOAK_THREE_PLANE_OK` only after the full rollback-contained lifecycle succeeds and always removes both containers.

The command locks the retained employee IAM projection as compatibility intake, verifies its exact row version and active employment/person/employee coordinates, and atomically records command evidence plus a bounded `employer`/`employment:<uuid>`/`workforce.employee` outbox intent. - The live internal-workforce probe drives all three states through the production NEON delivery repository and strict Studio consumer. It recovers from a forced provider outage, invokes the production Keycloak adapter when configured, creates Studio/NEON/MESH admission, grants the employee role only in NEON, and verifies suspension/deprovisioning advance every local principal's authorization epoch from 0 to 1 to 2 without deleting Person, employee or employment authority.
- The combined clean harness now runs both workforce variants against the same disposable canonical databases and real Keycloak realm. The internal path and the populated supported-upgrade path both emit `G5_INTERNAL_WORKFORCE_IAM_FULL_THREE_PLANE_ROLLBACK_OK`; the combined harness still removes both containers in all outcomes.

## Deliberately open

- The external-worker scenario is proven with the real provider and all three plane targets on both clean-build and supported-upgrade database paths.
- Buyer-requested supplier, supplier self-registration, internal-only Business Partner and customer paths still depend on the open G1/G2/G3/G4 controls.
- Internal workforce is proven on clean and supported-upgrade environments, but `document.workforce_iam_projection` remains a retained compatibility intake. It is not removal-eligible until measured production usage, consumer migration and the G0 compatibility window permit retirement.

The next G5 slices are the four Business Partner/customer scenarios as their G1-G4 command pipelines land. Independently, G0 must measure and drain the retained workforce IAM compatibility intake before any retirement migration is permitted.
