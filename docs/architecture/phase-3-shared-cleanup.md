# Phase 3 — Common/shared cleanup

Status: boundary implemented; duplicate-source removal remains an explicit, backed-up follow-up.

## Contract

`packages/shared` contains implementation that is reusable by at least two independent
deployment targets or is a platform contract required by those targets. It must not contain
application composition, product workflows, product API adapters, product configuration, or
temporary migration utilities. No generic catch-all package is introduced.

| Shared area | Allowed responsibility |
| --- | --- |
| `data-integration` | API/BFF contracts, metadata clients, query clients, transport and integration primitives |
| `platform-auth` | Authentication, sessions, authorization, identity and security policy primitives |
| `runtime-domain` | Runtime descriptors, records, documents, metadata-runtime and reusable runtime interaction primitives |
| `ui-platform` | UI primitives, navigation, shell, collaboration and reusable presentation components |
| `business-domain` | Business capabilities and rules reusable across products; no product screen or route |
| `shared-infrastructure` | Small cross-plane infrastructure utilities only |

## Current active authorities

The active pnpm workspace currently resolves the grouped canonical copies. The old flat paths
and excluded grouped copies are not active package authorities, but they are still source
manifests on disk. They must not be silently deleted because some contain divergent history.

The active package list is generated by `pnpm list -r --depth -1 --json`; the ownership matrix
records the result. `scripts/policy/verify-shared-package-purity.mjs` enforces that active shared
packages do not depend on application/product packages or import server/application
implementations.

## Classification decisions

Retain in shared when the package is a reusable platform/runtime/business capability:

- `api-client`, `api-contracts`, `metadata-client`, `query`, `bff-relay`, and exchange contracts
  remain in `data-integration`.
- `auth-common`, `auth-bff`, `identity-gate`, `session-plane`, and `session-store` remain in
  `platform-auth`.
- `runtime-contracts`, `runtime-shared`, `runtime-canvas`, `runtime-list`, line-item, add-item,
  and bulk-action runtime primitives remain in `runtime-domain`.
- `ui`, `theme`, `surface-kit`, `shell`, `brand`, `icons`, collaboration, workflow UI, and
  reusable content UI remain in `ui-platform`.
- `cascade`, `finance-rules`, `entity-print`, `print-templates`, and temporal/domain rules
  remain in `business-domain` when their public API is product-neutral.

The following require content-level extraction before relocation; they are not safe whole-package
moves because they contain both reusable runtime code and product-shaped behavior:

- `content-ui/src/purchase-invoice`
- `runtime-line-item/src/variants/sales.ts`
- any package files containing product route registration, product API adapters, or product-only
  configuration

Those files should move to the owning product/application package, while the neutral field,
document, line-item, and surface primitives remain shared. The extraction must preserve package
exports and be accompanied by consumer updates.

## Duplicate-source cleanup protocol

1. Generate the ownership matrix and purity report.
2. For each duplicate package name, compare tracked files with the active canonical authority.
3. Back up the complete duplicate directory outside the repository.
4. Remove only exact duplicates or obsolete excluded authorities.
5. Remove corresponding stale workspace exclusions and regenerate the lockfile.
6. Run install, policy, typecheck, tests, and build.

No package is removed merely because its path is excluded from pnpm. Exclusion means it is not
the active dependency authority; it does not prove the source tree is identical.

## Prohibited content

Shared packages must not add:

- app-specific screens, routes, shells, or navigation entries;
- product workflows or product-only field renderers;
- product API adapters or product configuration;
- migration scripts, one-time repair tools, or environment-specific seed helpers.

The canonical destination for such code is the owning product package under `packages/product`,
or the owning application composition package under `packages/apps`/`apps`, depending on whether
it is reusable across applications.
