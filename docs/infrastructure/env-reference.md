## 1. How env files work

### Execution contexts and files

| File | Runtime context | Who reads it | Edit rule |
|---|---|---|---|
| `stack/env/.env` | Docker Compose stack + host scripts | `compose.sh`, `api-up.sh`, `web-up.sh`, `validate-env.sh` | Primary non-secret bootstrap; edit config here, not credentials |
| `/opt/stack/athyper/secrets/.env` | Staging / production only | Same scripts; secrets win on key conflicts | Generated by `write-env-staging.sh`; mode 0600; never committed |
| `server/.env` | Local IDE only (`pnpm dev` without `api-up.sh`) | ts-node / tsx dev server via `dotenv` | Copy from `server/.env.example`; use host-reachable endpoints (127.0.0.1, not Docker service names) |
| `apps/{neon,mesh,admin}/.env.local` | Local IDE only (manual `pnpm dev`) | Next.js dev server | Optional convenience; not used by any script or CI |

### Two-file model (staging / production)

On the server, `ATHYPER_SECRETS_ROOT=/opt/stack/athyper/secrets`. When set, `compose.sh` builds a two-file `--env-file` chain:

```
--env-file stack/env/.env          # bootstrap: non-secret config (from repo template)
--env-file /opt/stack/athyper/secrets/.env   # secrets: passwords + keys (generated, 0600)
```

Secrets win on duplicate keys. All scripts that call `docker compose` use `${ENV_FILE_ARGS[@]}` to pass this chain. `validate-env.sh` accepts an optional second argument so it validates the merged view before `up.sh` runs.

`ATHYPER_SECRETS_ROOT` must stay **empty** on local dev. With an empty value, `ENV_FILE` resolves to `stack/env/.env` and all scripts use a single file.

### Local hostname translation

`api-up.sh` and `web-up.sh` translate Docker service hostnames to `127.0.0.1` before starting host processes. The env file uses Docker-internal names for compose; scripts rewrite them for host processes.

| Stack hostname | Host address |
|---|---|
| `dbpool-apps` | `127.0.0.1:6432` |
| `memorycache` | `127.0.0.1:6379` |
| `objectstorage` | `127.0.0.1:9000` |
| `docparser` | `127.0.0.1:9998` |
| `searchcore` | `127.0.0.1:7700` |
| `tracing` | `127.0.0.1:4317` |

For browser traffic, Traefik stays in Docker but routes to host dev servers:

| Browser host | Local upstream |
|---|---|
| `neon.athyper.local` | `host.docker.internal:3101` |
| `mesh.athyper.local` | `host.docker.internal:3102` |
| `admin.athyper.local` | `host.docker.internal:3103` |
| `api.athyper.local` | `host.docker.internal:4000` |

### Templates

| Template | Purpose |
|---|---|
| `stack/env/.env.example` | Local dev starting point — copy to `stack/env/.env` |
| `stack/env/staging.env.example` | Staging bootstrap (non-secrets) — deploy as `stack/env/.env` on the server |
| `stack/env/production.env.example` | Production bootstrap (non-secrets) — deploy as `stack/env/.env` on the server |
| `server/.env.example` | Local IDE runtime starting point — copy to `server/.env` |

`.bat` scripts are local-Windows-only and do not implement the two-file model. Use `.sh` equivalents for all staging and production operations.

### Configuration layer architecture

The platform has three distinct config layers. Each layer owns a non-overlapping concern; no config item should span two layers.

| Layer | Authoritative source | Loaded | Reloadable | Tenant-specific | Deploy to change |
|---|---|---|---|---|---|
| **ENV vars** | `stack/env/.env` + `secrets/.env` | Process start | No | No — process-level | Yes |
| **Kernel Config JSON** | `stack/config/apps/kernel.config.*.parameter.json` | Bootstrap, once | No | No — per realm (all tenants share) | Yes — intentional |
| **Feature Parameter Table** | `control.parameter_definition` + `master.tenant_parameter_value` | On-demand, cached | Yes (`runtime_reload` mode) | Yes — per-tenant override | No |

**Decision flowchart — where does a new config item go?**

```
1. Is it a secret, credential, or connection string?
   YES → ENV var. Stop. Never put it in JSON or the DB.

2. Does the server need it to identify which KC realm to trust,
   which public URL it is, or which tenants exist in a realm?
   YES → Kernel Config JSON. (deploy-gated IAM topology)

3. Does it vary per-tenant, or should it change without a deploy?
   YES → Feature Parameter Table.

4. Is it a realm-wide toggle where the deploy friction is intentional?
   YES → Kernel Config JSON.
```

**LOCKED sentinel.** Kernel Config JSON fields that reference infrastructure values carry `"LOCKED_USE_ENV_VAR"` as their value. The schema ([`stack/config/apps/kernel.config.schema.json`](../../stack/config/apps/kernel.config.schema.json)) defines `LockedSentinel` as a string matching `^LOCKED_USE_ENV_VAR`. The server config loader strips these at startup and reads the real value from the corresponding env var — keeping the JSON committable (no secrets) while expressing the full config shape in one file.

**Cross-references:**

| Resource | Path |
|---|---|
| Kernel Config JSON schema | [`stack/config/apps/kernel.config.schema.json`](../../stack/config/apps/kernel.config.schema.json) |
| Kernel Config per-env files | `stack/config/apps/kernel.config.{local,staging,production}.parameter.json` |
| Feature Parameter catalog (seed) | [`server/db/seed/platform/003_control/085_control_parameter_definition_contract.sql`](../../server/db/seed/platform/003_control/085_control_parameter_definition_contract.sql) |
| Parameter catalog status | [`docs/local/parameter-catalog-expansion.md`](../local/parameter-catalog-expansion.md) |

> **`keycloak.*` parameter rows** carry `control_level = external_provider`. These are read-only mirrors of KC realm settings for display in the admin UI — KC is the authoritative source. Do not add `runtime_reload` logic or tenant override support to these rows.
