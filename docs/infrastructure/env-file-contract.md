# Env File Contract

## Three execution contexts, three env files

| File | Runtime context | Who reads it | When to edit |
|---|---|---|---|
| `stack/env/.env` | Docker Compose stack + host-side scripts | `compose.sh`, `api-up.sh`, `web-up.sh`, `validate-env.sh` | Primary non-secret bootstrap file; edit config here, not credentials |
| `/opt/stack/athyper/secrets/.env` | Staging / production Docker Compose stack | Same scripts; secrets win on key conflicts | Generated by `write-env-staging.sh`; never committed |
| `server/.env` | Local IDE only (direct `pnpm dev` without `api-up.sh`) | ts-node / tsx dev server through `dotenv` | Generated from `server/.env.example` for local IDE runs; do not use Docker-only hostnames here |
| `apps/{neon,mesh,admin}/.env.local` | Local IDE only (manual `pnpm dev` without `web-up.sh` / `planes-up.sh`) | Next.js dev servers, if created manually | Optional convenience — not generated by `setup-env` and not used by any script or CI |

`server/.env` and app `.env.local` files are never the source of truth for anything outside
the IDE. `api-up.sh`, `web-up.sh`, and `planes-up.sh` parse `stack/env/.env` directly and
translate Docker hostnames to `127.0.0.1` before starting host processes. Direct IDE runs
load `server/.env`, so that file must use host-reachable names such as `127.0.0.1`, not
Docker-only service names such as `memorycache`.

`setup-env.sh` / `.bat` copies `server/.env.example` to `server/.env` for local
`server`, `runtime`, and `all` targets. It still has an `apps` target for the legacy
`apps/web/.env.local` template. The current Neon, Mesh, and Admin plane wrappers do not
require that file.

## Two-file model (staging / production)

On the server `ATHYPER_SECRETS_ROOT` is set to `/opt/stack/athyper/secrets`. When that
variable is non-empty, `compose.sh` builds a two-file `--env-file` chain:

```
--env-file stack/env/.env           # bootstrap: non-secret config (from repo template)
--env-file /opt/stack/athyper/secrets/.env  # secrets: passwords, keys (generated, 0600)
```

Secrets win on duplicate keys. All scripts that call `docker compose` — including
`api-up.sh`, `api-down.sh`, `api-restart.sh`, `web-up.sh`, `web-down.sh`, `web-restart.sh`,
`stack-profile/up.sh`, `stack-profile/down.sh`, and `stack-profile/logs.sh` — use
`"${ENV_FILE_ARGS[@]}"` to pass this chain.

`validate-env.sh` also accepts an optional second file argument so it can validate
the merged view before `docker compose up` runs:

```bash
# Local (single file):
bash validate-env.sh

# Staging (two-file merge):
bash validate-env.sh /opt/products/athyper/stack/env/.env \
                     /opt/stack/athyper/secrets/.env
```

## Local dev (Windows/macOS)

`ATHYPER_SECRETS_ROOT` must stay empty unless you are deliberately testing the server
two-file model locally. With an empty value, `ENV_FILE` resolves to `stack/env/.env`
and all scripts use a single `--env-file`. `api-up.sh` and `web-up.sh` translate
Docker service hostnames to `127.0.0.1` before launching host processes:

| Stack hostname | Host address |
|---|---|
| `dbpool-apps` | `127.0.0.1:6432` |
| `memorycache` | `127.0.0.1:6379` |
| `objectstorage` | `127.0.0.1:9000` |
| `docparser` | `127.0.0.1:9998` |
| `searchcore` | `127.0.0.1:7700` |
| `tracing` | `127.0.0.1:4317` |

For browser traffic in local development, Traefik remains the TLS entrypoint but routes
to host dev servers:

| Browser host | Local upstream |
|---|---|
| `neon.athyper.local` | `host.docker.internal:3101` |
| `mesh.athyper.local` | `host.docker.internal:3102` |
| `admin.athyper.local` | `host.docker.internal:3103` |
| `api.athyper.local` | `host.docker.internal:4000` |

Staging and production templates intentionally keep those upstreams on Docker service
names (`neon-web`, `mesh-web`, `admin-web`, `api`) so deployments never depend on a
developer workstation.

If you deliberately run the local `apps` profile fully in Docker, use the same Docker
service-name upstreams for that smoke test. Switch back to `host.docker.internal` before
daily UI development so code changes hot reload without image rebuilds.

## Templates

| Template | Purpose |
|---|---|
| `.env.example` | Local dev starting point — copy to `.env` |
| `staging.env.example` | Staging bootstrap (non-secrets) — deploy as `stack/env/.env` on the server |
| `production.env.example` | Production bootstrap (non-secrets) — deploy as `stack/env/.env` on the server |

The `setup-env.sh` script copies the appropriate template interactively.

Local `.env.example` exposes `GATEWAY_ACCESSLOG_REQUEST_PATH_MODE=drop` for developer
stacks. Staging and production compose overrides hard-drop Traefik `RequestPath`
regardless of env so auth callback URLs cannot land in gateway access logs with OAuth
`code` / `state`, login hints, or tenant/workspace context. The Loki logshipper also
redacts sensitive auth query values from container logs as a framework-log backstop.

## Windows .bat scripts

The `.bat` scripts under `stack/scripts/app/` and `stack/scripts/stack-profile/` are
**local Windows development only**.
They do not implement the two-file env model and will silently drop secrets-file
variables if used in staging or production. Use the `.sh` equivalents on Ubuntu for
all staging and production operations.
