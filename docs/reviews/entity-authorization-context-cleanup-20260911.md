# Entity authorization and context: repository review and cleanup

Status: repository review and proposed follow-up contract, with bounded BP UI cleanup deployed to shared DEV NEON on 11 September 2026 (MYT). This is not an activation, grant migration, new runtime schema, or replacement for existing qualification receipts.

## Recommendation

Keep one published entity authorization profile as the policy source for Records and Atlas. Separate identity, grants, stored ownership, selected work context, query filters and business eligibility. Bind each surface to an operation/resource reference; do not create independent grants for every visual nesting level.

The scope dimensions are not a universal hierarchy. A tenant boundary is mandatory for ordinary tenant data. Company and legal-entity relationships come from maintained master data; operating organizations can have explicit, effective-dated company assignments. Do not assume that an organization is always a child of one company, that a company grant implies an organization grant, or that a legal-entity ID substitutes for a company ID.

The proposed user experience has one transaction-context editor per record workspace. Shared master-data reads need no transaction selector. Scoped sections/actions request the editor only when their server decision requires context. The shell's working company can be a candidate default, never an implicit record owner or permission. Summary and directory filters remain separate optional query controls and never become Atlas command targets.

## Metadata-first contract: reuse and extend

Retain the current profile's `ownership`, `directory`, `recordReadOperation`, `operations`, `fieldPolicies`, `surfaces`, `relationships` and runtime binding/handler registry. Reuse the existing safe operation decision states: allowed, context required, verification required, workflow blocked, denied and unavailable.

Propose the following additions through the normal contract/parser/compiler lifecycle. These are design requirements, **not currently accepted JSON properties**:

1. A context requirement reference on an operation/provider: exact coordinate keys, owning resolver, multiplicity (single transaction target versus multi-value directory filter), permitted candidate sources, and compatibility/expiry rules. A presentation setting can choose a registered editor but cannot weaken the requirement.
2. An effective context-requirement DTO for each active surface/child entity, containing operation/resource references, missing coordinates, safe labels, decision/reference revisions and a candidate-resolution reference. It must distinguish `not_required`, `required`, `resolved`, `invalid` and `unavailable`; do not overload the user's authorization decision with preference state.
3. Candidate endpoints that evaluate the target capability, active memberships, scope propagation, effective dates and owner compatibility. Avoid leaking names of unauthorized organizations, companies or independent children.
4. A generic UI context controller consuming that DTO. Shell defaults, explicit URLs and existing form selections are candidate inputs. The server validates them before they become resolved context. Missing/denied candidates must not trigger fallback to a broader scope.
5. Atlas's context envelope references the same entity/descriptor/operation contract. Its page snapshot is advisory, never a reusable authorization permit. Every tool execution re-resolves current actor authority, ownership and field projection. An action cannot reuse a summary filter as its target.

Publication must reject unresolved ownership/context/provider references, incompatible coordinate/operation modes, field policies referencing absent operations, incompatible child ownership and unsupported resolver versions. Keep UI, bindings and runtime version compatibility closed on mismatch. Legal-entity support is a new registered capability, not a renamed company input.

## Resolution order

1. Verify actor, active tenant/plane, admission, assurance and current authorization revision.
2. Load the effective compatible entity descriptor and operation bindings for that tenant/plane/release.
3. For an existing resource, resolve its owner and independent children from storage. A URL or default cannot replace the stored owner.
4. Determine the particular operation's context requirements. A shared BP identity read requires no transaction context; a company configuration or transaction can require one.
5. Validate explicit context. If absent, a permitted shell/profile default may be suggested. Auto-selection is acceptable only for a unique, validated read/view candidate under a published rule; mutation targets stay explicit in the proposal/confirmation.
6. Evaluate current grants and explicit denials, propagation, field restrictions, MFA, separation of duties and business workflow preflight. Context selection is not an allow decision.
7. Return a safe decision and representation. Recheck before API execution, queued job execution, export completion/download and AI retrieval; invalidate caches/proposals when authority or context changes.

## Cleanup implemented in this change

- Removed the second inline `AccessScopeCard` from scoped sections. Their prompt opens the existing record-level editor.
- Removed the empty record context bar when neither context nor the editor is active. Shared BP browsing no longer starts with two “Not selected” values.
- Removed repeated directory-visibility and selected-context prose from the editor. Kept compatible organization/company selection and its existing apply path.
- Moved transaction eligibility behind an optional disclosure and deferred eligibility requests until it is opened.
- Publish BP context to Atlas only when the corresponding summary is loaded for the requested record; use the scope returned in that summary.
- Corrected the hardcoded BP home description so it no longer claims all partner master data is organization-owned.

The BP UI cleanup is deployed to shared DEV NEON. No grant, active entity descriptor, ownership resolver, scope fallback or enforcement mode was changed. The summary filter remains independent.

## Generic Atlas continuation — local implementation

The Atlas manage-context resolver now retains an independently owned collection's work coordinates for the visible-page query and selected-record query, after the owner validation call. Previously those row queries used directory filters alone, losing the child's selected organization. Mixed parent directory filters on these collections are rejected until a registered owner contract supports that combination. This is metadata-driven through `collectionRelationship`, including non-BP entities.

Shared record browsing now derives tenant-directory behavior from the published `directoryScope`, rather than a NEON/BP name check. Independently owned collections are excluded from that rule, and the owning record read plus authorized list membership remain mandatory. Work context is still advisory and does not authorize a command.

Validation: 21 focused Atlas context tests passed, including non-BP collection scope retention, unauthorized selected rows, absent/unauthorized/mixed coordinates, generic shared-master browsing and owning-service denial. These changes are local and are not present in the already packaged `c377e1dc…` image; that image's receipts must not qualify this successor source.

The remaining BP legacy AI admission and case-owner branches have not been retired. Global and legal-entity resolver keys remain unsupported: the current profile/evaluator requires a tenant and has no global authority mode, and adding keys alone would not provide stored ownership or valid grant semantics. These require versioned contracts, registered owning services and qualification, not aliases for existing tenant/company scopes. No enforcement approval or activation is recorded by this continuation.
