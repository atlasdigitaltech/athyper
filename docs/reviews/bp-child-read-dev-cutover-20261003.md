# BP child-read cutover build — existing DEV, 3 October 2026

**Source changes and safety gates implemented; DEV cutover is not complete.** The
owner selected the existing DEV deployment. No additional deployment was created,
no DEV permission or grant was changed, and no approval or publication receipt
was manufactured.

## Implemented

The seven child `operation.json` read operations no longer declare the redundant
permission codes. Their entries were removed from the draft registry catalog.
Published releases, captured historical catalogs and immutable seed SQL remain
historical evidence; they were not rewritten to make a search return zero hits.
Write, reveal, protection and MFA properties are unchanged.

Each child core now declares `directoryScope.parent` with its exact BP
relationship key. BP's core explicitly declares the corresponding
`entityRelationships`; lowering must preserve those declarations in the runtime
record presentation. Owner and tenant fields are immutable, hidden UUID fields,
not visible list identities. These changes do not introduce a parent permission
alias on the child: the shared resolver reads and authorizes the actual parent.

The split publication validator requires the enforcing runtime members. It
checks matching parent declarations, same-plane parent coverage, exact child and
tenant mappings, immutable required fields, a readable parent title and declared
read operations. Nested required-parent chains fail closed. Runtime
still rechecks the current parent descriptor hash and record. Company and
organization scope cannot fall back to tenant scope when the resolver is absent.

All 14 owner/tenant field bindings were checked against the existing DEV schema;
see [schema evidence](bp-child-read-dev-owner-mappings-20261003.json). Banking
uses `master.v_business_partner_bank_account` ownership and **link identity**:
the existing security-invoker view resolves BP/customer/supplier links to their
BP. A bank-account ID alone does not identify the scoped link. This is a source
mapping correction, not proof that the missing banking projection reader exists.

The new [fresh-baseline correction](../../server/db/ddl/planes/neon/authz/28_retire_bp_child_reads.sql)
runs after the historical Neon seeds. It retires precisely the seven codes and
preserves their catalog identities. It refuses a wrong plane, an incomplete
catalog, any active publication or any dependent permission FK other than scope
catalog rows. It does not delete grants or change roles on a populated database.
The existing terminal lifecycle rejects retired-to-published transitions. No
applied migration or historical seed hash was changed. Full fresh-foundation
installation has not been rehearsed by this change; the bounded correction and
terminal lifecycle were exercised with the actual repository trigger functions.

## Cleanup tool corrections

The tool now reads descriptor content from payload `artifacts`, matching the
actual compiled publication shape; `release.artifacts` contains manifest entries,
not descriptors. The database fixture now uses that same structure. The report
also identifies active publication references and exact group-role scope edges.
A read-only report does not require an audit actor; guarded apply generation still
requires an explicit actor, tenant scope, exact successor release/hash and parent
relationship. No unresolved manifest can generate apply SQL.

Retirement sets the actor context and leaves lifecycle evidence to the existing
triggers. It no longer overwrites prior status evidence before the immutable
history guard runs. Roles must already be prepared through their governed
modification process. Apply removes only the reviewed role-permission links,
preserves role/group membership and catalog history, and refuses unresolved
active references. The fresh-install correction must never be substituted for
this DEV process.
