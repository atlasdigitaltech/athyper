# Transaction-bound authorization writers

> Local-development baseline update: the 16 scripts listed in [SQL DDL consolidation](sql-ddl-consolidation.md) have been folded into `server/db/ddl/` and removed from the migration manifests. Use the canonical DDL for a fresh local database. Migration commands and migration-path test results below describe the earlier implementation and are historical, not current setup instructions.

The canonical production implementation is `KyselyAuthorizationManagementRepository`, composed through `createKyselyAuthorizationManagementUnitOfWork`. The host uses that factory when authorization-management dependencies supply rollout policies and a writer gate without a custom unit of work. `writerDatabases` can supply separate exact-plane connections; otherwise the existing metadata connections are used. No route or mutation flags are enabled by this change.

The writer uses the verified plane, tenant and actor, locks tenant-owned rows, enforces expected versions, and preserves the DDL lifecycle/approval/parent-edit guards. Unknown payload fields are rejected. Role and group definitions created here are custom; managed definitions cannot be edited. Compiler-owned operation projections and browser enrollment remain restricted to their dedicated publication and IAM step-up paths, returning explicit 403 errors from this generic writer.

Every successful command stores an immutable `authz.management_receipt`, a success audit record, and an outbox event in the effects transaction. Existing DDL authority-capture triggers also produce authorization invalidations and advance their epochs. Receipts bind the complete command to tenant, plane and principal. Matching retries return the original version without duplicate management audit/outbox events. Changed content or stale versions produce 409. Approval retries verify their receipt before checking the now-decided request. They still require current approval permission and a qualified writer gate.

Create commands omit `expectedVersion` and may supply `resourceId` for a chosen UUID. Updates, decisions, revocations and child deletion require `resourceId` and a positive `expectedVersion`. Existing database rows start at version 1; database triggers advance versions on updates. Removing a role-permission or pending-delegation child produces a terminal receipt at the prior child version plus one. A pending delegation remains pending; this API has no delegation-approval command and does not invent approval evidence.

Apply `20260917_authorization_management.sql` after the preceding migrations in the selected plane manifest. Fresh-install manifests include `common/authz/13_management.sql`. The migration adds row versions, receipts, the audit contract and a dedicated NOLOGIN `athyper_authorization_writer` role. It does **not** grant that role to ordinary application connections. Provision the approved writer login with the existing application dependencies and this role, then supply its connections through `writerDatabases`. Database permission/schema failures return 503; qualification and mutation flags still govern application enablement.

Three trigger-only validation routines run with fixed search paths as security definers so they can inspect private scope helpers and related authority rows. The helpers themselves remain inaccessible to application roles; source-table tenant RLS still gates mutations. Device enrollment retains its self-only insert policy. The writer role can read and revoke an existing device within the verified tenant.

Legacy and shadow writes require `legacyTransactionBinder(tx, context)` to return the **actual legacy** writer and its audit sink using that transaction. The canonical writer is never used as a legacy fallback. No legacy mutation implementation or authoritative legacy storage mapping was found in this repository. Until that target is identified and bound, legacy writes return `AUTHZ_LEGACY_WRITER_UNAVAILABLE` (503); approval requests may fail earlier because the legacy override reader is absent. External IAM effects must be represented by a transactional outbox, not inline remote calls.

Validation completed against full fresh Studio, Neon and Mesh DDL and a populated Neon schema restored to the pre-version/receipt shape before applying the migration. Nine acceptance cases per target cover real roles, groups, assignments, denies, delegation children, overrides, ACLs and remembered-device revocation; idempotency; concurrent versions; tenant isolation; actor separation; database audit/outbox rollback; invalidation emission; and protected command rejection. The migrated existing role rows were checked to start at version 1. Test ports are not substituted for the canonical writer or audit/outbox implementation in these acceptance cases.

Local application deployment, writer-login provisioning, writer-switch qualification and authenticated browser acceptance were not performed. Legacy storage selection is still required before legacy/shadow enablement.
